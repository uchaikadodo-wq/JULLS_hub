# Серверная сборка Lookin.Team Base

Это отдельная конфигурация для `base.lookin.team`, VPS amd64 с 2 GB RAM.
Она не заменяет `compose.local.yaml`. Подготовка файлов и локальная проверка
не означают, что приложение перенесено или опубликовано на VPS.

## Состав

- Свой PHP-FPM 8.3.36 из официального закреплённого образа, без dev-сервера Artisan.
- MySQL 8.4.13, та же ветка LTS/СУБД, отдельный постоянный том. Локальная СУБД
  не обновляется и не заменяется при подготовке этой конфигурации.
- Свой образ Caddy 2.11.7 со статическими файлами, автоматический HTTPS.
- Исходники BookStack v26.09.2 не правятся. Тема включена в образ отдельно.
- Исправленные lock-файлы лежат в `dependencies/`, явно подключаются в Dockerfile.
  Исходные корневые lock-файлы сохранены. Сводка версий и хешей — `dependencies/changes.json`.

Сборка выполняется на машине разработчика для `linux/amd64`, а не на VPS с 2 GB
памяти. Не переносить ARM-образ с Mac как готовый amd64-образ. Версионные теги
app/web должны соответствовать одному выпуску; при переносе проверять также
image ID/контрольную сумму архива, записанные в манифесте выпуска.

```sh
docker buildx build --platform linux/amd64 -f server/Dockerfile --target app -t lookin-base-app:v26.09.2-20261030-1 --load .
docker buildx build --platform linux/amd64 -f server/Dockerfile --target web -t lookin-base-web:v26.09.2-20261030-1 --load .
```

Базовые образы закреплены SHA256. Build context ограничен allowlist-файлом
`Dockerfile.dockerignore`: туда не входят `.env`, дампы, реальные загрузки,
host vendor/node_modules, Git, private-папки и SSH-ключи. Установка зависимостей
выполняется на стадии сборки с отключёнными hooks/plugins. Явно выполняются
проверенные команды сборки JS/CSS и генерации autoload/лицензий.
В конечных образах нет npm, Node, Composer, PHPUnit и dev-зависимостей.

## Данные и ограничения

Именованные тома:

| Том | Содержимое |
|---|---|
| `database` | Записи MySQL: статьи, пользователи, роли, ключи и настройки |
| `storage` | Защищённые вложения/изображения, сессии, кэш, журналы |
| `public_uploads` | Публичные изображения оформления, например логотип |
| `caddy_data` | Сертификаты и ключи HTTPS |
| `caddy_config` | Данные Caddy |

Эти тома сохраняются при замене app/web. `docker compose down -v`, очистка
volumes и ручная замена рабочей БД локальным дампом не являются способом
обновления приложения. Не выполнять их при обычной доработке.

App/web работают как UID 1000 с read-only корнем, записывают только тома/tmpfs.
Примерные лимиты контейнеров: MySQL 768 MiB, PHP 512 MiB, Caddy 128 MiB.
PHP-FPM запускает не более трёх обработчиков, MySQL buffer pool — 128 MiB.
Это начальные ограничения для пилота, не доказательство достаточной
производительности под нагрузкой. Сборка/сжатие больших PDF/ZIP может потребовать
больше ресурсов или дополнительных ограничений запросов.

Приложение и БД подключены только к внутренним сетям. Caddy имеет внешнюю сеть
для HTTPS и внутреннюю для FPM; прямого доступа Caddy к БД нет. Внешние
соединения приложения пока отключены изоляцией: SMTP, SSO, webhooks и другие
интеграции потребуют отдельно продуманного разрешения исходящего доступа.
Не считать это исправлением уязвимостей библиотек.

Опубликованы только 80/443 TCP у Caddy; FPM/БД не публикуются. Docker-публикации
могут обходить UFW, поэтому при фактическом развёртывании необходимо проверить
внешнюю доступность и forwarding, а не только вывод UFW. MCP не включён в этот
Compose: его сетевой транспорт с индивидуальной аутентификацией готовится отдельно.

## Секреты и подготовка к первому переносу

`deploy.env.example` — только параметры Compose. `app.env.example` — поясняющий
шаблон приложения. Настоящие файлы хранятся вне Git/контекста сборки, на VPS
предлагаются `/opt/lookin-base/secrets/` (0700) и файлы внутри (0600).

Перед переносом нужно:

1. Согласовать окно переноса и отдельно разрешить передачу/публикацию на VPS.
2. Проверить свежий бэкап текущей локальной БД и загрузок. На время снимка
   приостановить изменения, чтобы не потерять последние статьи/права.
3. Создать новые серверные пароли MySQL, одинаковый пароль приложения записать
   в `app.env` и файл секрета `db-password`, отдельный root-пароль — в `db-root-password`.
4. **При переносе существующей БД сохранить её APP_KEY.** Не генерировать новый
   автоматически и не печатать его в чат/логи. Новый APP_KEY создают только для
   действительно пустой новой установки, не для переноса текущей базы.
5. Указать настоящий операционный email для ACME. `SITE_ADDRESS` и `APP_URL`
   должны соответствовать `base.lookin.team`; Secure cookie включён.
6. Пересмотреть стартовые аккаунты и токены: локальный тестовый ключ агента не
   раздавать и не использовать как общий серверный ключ. Заменить тестовые
   credentials администратора согласованным способом, не теряя его доступ.
7. Восстановить БД и загрузки в новые серверные тома и проверить их. Тестовые
   тома проверки сборки не использовать в качестве исходных данных.

Приложение пока настроено на `MAIL_DRIVER=array`: письма не отправляются и не
пишутся с токенами восстановления в лог. Для приглашений и сброса пароля
нужна отдельно настроенная почта; ручные аккаунты пилота не заменяют её.

## Явные операции после отдельного разрешения на перенос

Команды ниже — инструкция, **не указание выполнять публикацию сейчас**. Все
пути/секреты/образы должны быть предварительно подготовлены и проверены.

Всегда указывать отдельный `--env-file` и `-f server/compose.yaml`; не полагаться
на локальную `.env` с `COMPOSE_FILE=compose.local.yaml`. Проверка не должна
печатать итоговый config с секретами в общий лог:

```sh
docker compose --env-file /opt/lookin-base/deploy.env -f server/compose.yaml config --quiet
docker compose --env-file /opt/lookin-base/deploy.env -f server/compose.yaml up -d --wait db app
```

Далее явно восстановить согласованный SQL-дамп и соответствующие загрузки/APP_KEY.
Способ передачи и команды импорта составляются для конкретного проверенного
бэкапа перед переносом; не вставлять SQL-пароль в командную строку. Перед
изменением схемы — отдельный бэкап. Миграция выполняется вручную один раз:

```sh
docker compose --env-file /opt/lookin-base/deploy.env -f server/compose.yaml exec -T app php artisan migrate --force
docker compose --env-file /opt/lookin-base/deploy.env -f server/compose.yaml exec -T app php /opt/lookin/release-check.php
```

Если приложение сообщает об открытой регистрации/публичном просмотре, после
проверки настроек явно закрыть их через `release-check.php --close-access` и
повторить проверку. Скрипт не меняет APP_KEY или пароли и не выполняет миграции.
Режим по умолчанию проверяет, ничего не меняя.

Только после проверки восстановления, ролей, секретов, путей хранения,
согласования firewall/публикации и резервного копирования запускать `web`.
До этого HTTPS в интернете не проверен и сертификат не считается выпущенным.

## Бэкап и обновление

Сохранять согласованный SQL-снимок, `storage/uploads`, `public_uploads`,
конфигурацию и соответствующий APP_KEY. Копии с секретами шифровать/ограничивать
по доступу. Хранить отдельную копию вне VPS. До запуска реальной работы выбрать
хранилище, периодичность и срок хранения; проверить восстановление на отдельной
базе. Это ещё не настроено данным Compose. Постоянная копия документов на Mac
для ежедневной работы не нужна.

Перед обновлением кода: бэкап → проверка новых образов/темы/зависимостей →
при необходимости согласованные миграции → замена только app/web → контроль
доступа/статей/вложений. БД и тома остаются серверными. Старые версии app/web
сохранить для отката; откат образа не отменяет миграцию БД. При несовместимой
схеме потребуется восстановление согласованного снимка с учётом новых записей.

Остановка без удаления данных:

```sh
docker compose --env-file /opt/lookin-base/deploy.env -f server/compose.yaml stop
```

## Локальные проверки

```sh
python3 scripts/check-server-release.py
```

Скрипт сначала проверяет итоговый production config, затем создаёт отдельный
проект с вымышленными данными, собственной БД и единственным портом
`127.0.0.1:8082`. Проверяет запуск amd64-образов под эмуляцией на Mac, миграции,
вход, тему, поиск, скачивание вложений и экспорт, запрет API-записи, защиту MIME
и сохранение данных при пересоздании app. В конце останавливает только свой
проект, сохраняя его тестовые тома для разбора. Не читает и не импортирует
рабочие статьи. Журнал и синтетические секреты — в игнорируемой private-папке.

PHP-тесты исправленной библиотеки выполняются отдельно на восстановленной
тестовой копии; JS-тесты — в образе `js-tests`, без сети. Это не заменяет
проверку запуска на физическом VPS, нагрузочные проверки и тестирование
сертификата, реальной почты, внешнего MCP и резервного хранилища.
